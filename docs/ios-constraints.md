# iOS 実機で判明した制約

**検証環境: iPhone XR / iOS 17.5.1 / Safari 17.5（2026-08-29〜30）**

コードが素直でない箇所は、ほぼすべてここに理由がある。
推測ではなく実機で測った結果だけを書く。

## カメラは同時に1つしか掴めない

映像トラックが生きている状態で2本目の `getUserMedia({video})` を呼ぶと、
**1本目の映像トラックが `ended` になる。** 音声トラックは生き残った。

```
20:41:01.079 2本目 getUserMedia({video}) を要求 — 直前の音声: live -46.9dBFS
20:41:01.283 [映像] ended / readyState=ended
20:41:06.658 5000ms後 — 音声: live ← 健在
```

### 設計への影響（重要）

- **起動時に `{audio, video}` を一度だけ取得し、以後は取り直さない**
- **会話の切断でトラックを止めてはいけない。** ウェイクワード待機に生きたマイクが要る
  → `RealtimeSession.stop()` は PeerConnection を閉じるだけ
  → `MediaController.releaseAll()` はアプリ終了時のみ
- カメラの内/外を切り替えるときだけ、**先に映像トラックを止めてから**取り直す。
  会話中は切り替えられない

## フレーム取得は思ったより遅い

```
フレーム取得 576x1024 / 178KB / 328ms
```

JPEG エンコードがメインスレッドで走るため。**画像質問の1〜3秒予算に必ず計上すること。**
短縮の余地: 長辺を512pxへ / 品質を下げる / OffscreenCanvas をワーカーで回す。

## Wake Lock は画面が隠れると解放される

```
20:42:01 Wake Lock が解放された / 画面表示状態: hidden
20:42:46 画面表示状態: visible → Wake Lock 取得（復帰時）
```

仕様通りの挙動。**`visibilitychange` での取り直しが必須。**

## 音の出力先 — 疑ったが問題なかった

当初、マイク取得中に音が**受話口**（画面上部）から小さく鳴る現象を観測し、
「常設端末として成立しない」最大のリスクとして扱った。
W3C Audio Session の説明書も `play-and-record` を
「スピーカーではなく受話口へ回すためのもの」と記述している。

`spike/routing.html` で総当たりした結果、**再現しなかった。**

| 条件 | 聞こえ方 | マイクの拾い |
|---|---|---|
| マイク取得中 + WebAudio（音声＋映像で取得） | スピーカー | -31.5 dBFS |
| マイク取得中 + WebAudio（音声のみで取得） | スピーカー | -31.0 dBFS |
| `audioSession.type = "playback"` | スピーカー | -80.9 dBFS |
| `audioSession.type = "play-and-record"` | スピーカー | -27.2 dBFS |
| **WebRTCループバック（音声のみ）** | スピーカー | -34.7 dBFS |
| **WebRTCループバック（映像あり）** | スピーカー | **-73.1 dBFS** |

- **どの条件でもスピーカーから鳴った。**
  「映像トラックを保持していないと受話口になる」という仮説を立てて検証したが、
  音声のみの取得でもスピーカーだった。**反証済み**で、実装上の制約にはならない
- **マイクはどの条件でも生存した。** `type = "playback"` 中に話しかけても
  -30.0 dBFS で拾えた（通常時 -27.7 dBFS）
- **エコーキャンセルは効いている見込み。** 第1段階の実経路にあたる
  WebRTCループバック（映像あり）で、スピーカーから聞こえているのに拾いは -73.1 dBFS。
  WebAudio 直接再生の -31.5 dBFS より40dB以上低い

### 未解明として残る点

最初に観測した受話口の現象が何によって起きたのかは特定できていない。
再現した条件との差は `noiseSuppression: false` / `autoGainControl: false` を
指定していた点。本アプリはこれらを既定値（有効）で使うため実害は低いと判断し、追跡を打ち切った。
**第1段階以降で受話口の症状が出たら、まずこの2つの制約を疑うこと。**

## マイクは AEC を有効にするとゲインが上がる

```
AEC=true   ノイズフロア -27.7 / -35.6 dBFS
AEC=false  ノイズフロア -53.0 / -56.5 dBFS
```

2回とも約25dBの差。`echoCancellation: true` にすると iOS が音声処理ユニット側に
切り替わり、ゲインが大きく上がる。**遠くから話しかける常設端末には有利な性質。**

## Vosk は iOS Safari で動く

モデル（48MB）の読み込みと連続認識、どちらも動作した。
ただし**遠くの声は届きにくい。** カフェ（最悪条件）では入力ゲインを10倍にして
ようやく実用の入口だった。静かな環境での再調整が必要。

`AudioContext({ sampleRate: 16000 })` を直接要求すると通る。
このため自前のリサンプラは不要になった。

## その他

- **iPhone XR の iOS 上限は 18**（iOS 26 で対象外）。Wake Lock は 16.4+ なので問題なし
- **`getUserMedia` と Wake Lock は保護されたコンテキストでしか動かない。**
  LAN 経由でも HTTPS が要る（`scripts/dev-proxy.mjs` がそのため）
- 給電したまま画面を点けっぱなしにするとバッテリーが劣化する。UI を黒基調にしてある

## 未検証

- **アラーム音がマナースイッチで消音されないか。** アラームとしては致命的
- 数時間の連続稼働での安定性（Wake Lock の取り直しは短時間では確認済み）
